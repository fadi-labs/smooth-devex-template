# ai-understanding — AGENTS.md

## TL;DR

An Understanding is the input and outcome of a session's memory, written for another agent to act on — reusable, terse, structured, and holding only what no code file or knowledge document already holds. `--export` writes them to `<subject>-<yyyyMMdd-HHmm>/<slug>.md` files under the gitignored `.context/understandings/`; the store is disposable by design, so `--publish` — a zip under `.context/understandings-publish/`, handed over out of band, never a tracked repo path — is the only path by which knowledge leaves a workspace. Never weaken the `scope` gate that governs it.

## Non-Negotiables

- **Never drop the subject folder.** `<subject>-<yyyyMMdd-HHmm>/<slug>.md`. The subject is what keeps a session's lessons legible as a body of work months later, and it was an explicit design correction from the user — not an incidental layout choice. Equally, do not reintroduce a folder per unit: a unit is one file, and the rare unit carrying artifacts puts them in a sibling `<slug>.assets/`.
- **Never make the index subject-first for retrieval.** The index groups by subject for browsing, but lists every unit with its question, because an agent has a question in mind rather than a subject. An edit that makes a reader open a subject before seeing questions files knowledge under the one label nobody searches by.
- **Never let a write edit or delete an existing copy of a slug.** An improved Understanding is re-written in full into *this export run's* stamped folder and carries `provenance.supersedes`; previous copies are immutable history (LADR-010). An edit that adds an "overwrite", "force", or merge-in-place path deletes knowledge the user chose to keep, and erases the revision depth that tells a reader how settled the knowledge is.
- **Never let `--portable-only` publish a `repo-specific` unit.** That filter is the only thing preventing a local quirk from being shipped to another repo with provenance that makes it look universally verified.
- **Never add remote fetching to this skill.** `--consume` takes a local archive path only; how the zip arrived (mail, chat, a drive) is out of band and not this skill's concern (LADR-008). A transport implementation here would be a second provenance model and a second merge semantics next to `ai-asset-sync`'s.
- **Never write an export run into an existing stamped folder, and never carry an unchanged unit forward into a new one.** A stamped folder *is* one export run: it holds only what that run produced — new and improved units — and a run that produced nothing creates no folder at all (LADR-010). _(This reverses LADR-007's folder-reuse rule, which required the opposite. The subject **name** is still reused for a body of work; the stamp is per-run.)_
- **Never make a slug unique store-wide again.** The same slug in two stamped folders is the versioning mechanism, not an error: the newest stamp is the current version and the rest are history. An edit that reinstates a `duplicate_slugs` check, or makes the index list every copy, disables versioning silently — every stale revision becomes current again and an agent asking one question gets several conflicting answers (LADR-010).

## Architecture Decisions

### LADR-001 — Working store is local and disposable; publish is the durability boundary

- **Date:** 2026-09-19 · **Status:** Accepted — publish destination superseded by LADR-008
- **Context:** Understandings could live in a tracked path (`.agents/understandings/`, syncable immediately) or in the gitignored `.context/` tree. A tracked store makes every encoded unit instantly shareable — and instantly permanent. Most of what a session produces is not worth keeping, and review pressure at encode time is exactly when the knowledge is least settled.
- **Decision:** The working store is `.context/understandings/` (local, gitignored, per-workspace) and `--export` writes the session's knowledge there. Leaving the workspace is a separate, human-approved `--publish` step. _(Originally with the tracked `.agents/understandings/` as its destination; LADR-008 retired that — publish now produces an archive under `.context/`, and nothing reaches git.)_
- **Consequences:** Encoding stays cheap and low-stakes, so agents propose freely. Review happens once, at publish, when it is clear which knowledge held up. Trade-off: a workspace destroyed before its publish loses its memory — accepted, because the alternative pollutes shared memory with unreviewed observations. Nothing is seeded: a workspace that never publishes carries no archive.

### LADR-002 — `scope` is a first-class field, not a judgment made at publish time

- **Date:** 2026-09-19 · **Status:** Accepted
- **Context:** Deciding portability when publishing means judging units long after the session that produced them, with none of the context that would reveal whether a behavior was general or an artifact of this repo's setup.
- **Decision:** Every Understanding declares `scope: portable | repo-specific` at export time, while the evidence is fresh. Publish filters on the field rather than re-deciding.
- **Consequences:** Publishing is mechanical and auditable. The judgment sits where the information is. Bias toward `repo-specific` when unclear: leaving knowledge behind costs one rediscovery, while publishing a false universal costs every consumer that acts on it.

### LADR-003 — `INDEX.md` is generated, and is a reference table only

- **Date:** 2026-09-19 · **Status:** Accepted
- **Context:** An index maintained by hand drifts from the units, and an index that inlines the knowledge defeats its own purpose — an agent that must read the whole index to find one applicable Understanding has already paid the tokens it was trying to save.
- **Decision:** `scripts/understanding_index.py` regenerates `INDEX.md` from frontmatter. Rows carry unit, description, question, scope, confidence, updated — reference data for matching, never the knowledge itself. `question` lives in frontmatter only, so the index cannot contradict the unit.
- **Consequences:** Importing is a two-step read: match questions in the index, then open only matching units. The script validates as it goes (required fields, slug/folder agreement, enum values, dangling `[[links]]`, and units left at the old single-level depth) **on current versions only** — superseded copies are immutable history and exempt (LADR-010) and exits `1` on problems while still writing the index, so drift surfaces without blocking the write. There is no INDEX template — the generator is the single source.

### LADR-004 — Subject folder groups; the question still retrieves

- **Date:** 2026-09-19 · **Status:** Accepted
- **Context:** A session usually has one main subject, and splitting its lessons into sibling top-level folders loses that — the work reads as five unrelated facts a month later. The obvious fix, making the subject the addressable unit with several Understandings inside it, breaks two things: retrieval (most of what a session teaches applies to work that has nothing to do with the session's subject) and publish granularity (one subject folder routinely mixes `portable` and `repo-specific` units, so it cannot be moved wholesale).
- **Decision:** `<subject>/<slug>.md`. The subject folder groups for browsing; the file stays the addressable unit for retrieval, versioning, `[[links]]`, scope filtering, and confidence. The generated index groups by subject but lists every unit with its question. A `[[slug]]` addresses the knowledge rather than any one copy of it, so a link never names a subject. _(Amended by LADR-010: slugs are no longer unique store-wide — a slug repeated across stamped folders is a version chain, and the index resolves it to the newest. The clause that a session adding to existing work reuses its folder is retired with it.)_
- **Consequences:** A session stays legible as a body of work without knowledge becoming findable only through its origin. Cost: every Understanding needs a subject (`_unfiled/` absorbs the ones with no topic). Units left in an older layout — at the store root, or in a per-unit folder — are reported as a problem naming the fix rather than silently skipped.
- **Superseded sub-decision:** the unit was first a folder (`<slug>/UNDERSTANDING.md`) to namespace evidence artifacts. That cost a directory level on every unit to serve a case that had not occurred in any of the first five, all of which quote their evidence inline. The unit is now a file; artifacts, when a unit genuinely has them, go in a sibling `<slug>.assets/` whose name derives from the slug and so cannot collide. The rejected objection — that publishing would have to "reach inside" a subject folder — was wrong: the file is the unit, so per-unit publish is a file copy.

### LADR-005 — Record inherited lineage, not the session's reasoning

- **Date:** 2026-09-19 · **Status:** Accepted
- **Context:** Import wrote nothing back, so the store had no evidence of which knowledge was ever used — a unit nothing inherits is indistinguishable from one that simply has not come up, which makes pruning guesswork and leaves no blast radius when a unit turns out wrong. A proposed alternative modelled the export on the novel's generational framing with four dimensions per unit: inherited knowledge, the conflict encountered, the cost-benefit reasoning behind the agent's adaptation, and the resulting lesson.
- **Decision:** Take the lineage only. `provenance.inherited` lists the `[[slug]]`s a session loaded **and acted on**. The other three dimensions are rejected: "the conflict encountered" and "the reasoning behind the adaptation" are agent-centric — they record what the agent did and why it adapted, which is a session log with better vocabulary — and "the resulting lesson" is the Understanding itself under another name.
- **Consequences:** One optional list buys a usage signal, a lineage graph, and the ability to find what depended on a unit later found wrong. The store stays knowledge-centric: what is true and when it applies, never the journey that produced it. A bracketed entry must resolve; unbracketing records an ancestor that has since been pruned or promoted, so removing a unit does not either break the index permanently or force rewriting history. Not adopted: machine-validating the *quality* of recorded reasoning — a checker can only confirm a field is non-empty, which teaches agents to write filler into a required box.

### LADR-006 — Publish defaults to every unit; `--portable-only` filters for the cross-repo case

- **Date:** 2026-09-19 · **Status:** Accepted
- **Context:** The original default (`--publish` = `scope: portable` only, `--all` for the rest) was tuned for cross-repo publishing when the common case is same-repo team sharing — handing a teammate the memory for the repo they already work on. Measured on a real store of 8 units: `--publish` produced 1 unit, 2.1 KB; the same store with `--all` produced 8 units, 16 KB. Everything about the repo's own build, CI and tooling — the part a teammate most needs — was filtered out by default, and the common operation required a flag while the rare one was free.
- **Decision:** `--publish` archives **every** unit by default. `--portable-only` restricts the archive to `scope: portable` units, for the case where the destination is another repository. `--all` is retired from publish; it keeps its distinct, unrelated meaning on `--export` (skip the pre-write cut).
- **Consequences:** A same-team archive is complete by default — the common operation needs no flag. Cross-repo publishing now requires remembering `--portable-only`, and forgetting it ships `repo-specific` knowledge elsewhere — which is why the guardrail above moves to attach to `--portable-only` rather than disappearing. `scope` (LADR-002) is unaffected: it is still declared at export time and is still the only thing `--portable-only` filters on. Filtering a subset also means a published unit's `[[link]]` can point outside the archive; the zip-publish worktask carries the fix (drop the brackets, keep the entry) as a consequence of this decision. **Rejected alternative:** keep `portable-only` as the default and require `--all` for the complete case — rejected because it optimizes for the rarer cross-repo operation at the cost of the common same-repo one.

### LADR-007 — Subject folder is stamped with when it was created; slugs stay unique store-wide

- **Date:** 2026-09-19 · **Status:** Accepted — the stamp stands; the uniqueness and folder-reuse clauses are superseded by LADR-010
- **Context:** LADR-004 gave the subject folder a name for browsing, but a bare `<subject>/` says nothing about when the body of work it groups was captured, and two sessions independently choosing the same subject name land their lessons in one folder. A timestamp could mean two different things: version each write (slugs unique only within a subject), or name the folder once at creation and keep slug uniqueness store-wide.
- **Decision:** `<subject>-<yyyyMMdd-HHmm>/`, 24-hour, UTC, set once when export creates the folder and never bumped — freshness is already `updated`'s job. Slug uniqueness stays store-wide: a session adding to work already captured **reuses the existing stamped folder** rather than minting a new one. _(Superseded by LADR-010, which took the rejected branch below: the stamp now versions each export run, a slug is a version key, and a run that improves a unit mints a new folder. The stamp format, its UTC basis, its set-once rule and `_unfiled`'s exemption are unaffected.)_ `_unfiled` is exempt, since it is a permanent catch-all rather than a body of work. Publish carries a subject folder's stamp verbatim; it never re-stamps, since that would overwrite when knowledge was *learned* with when it was *sent*.
- **Consequences:** A reader sees a body of work's age before opening anything, and two sessions can never collide on a folder name. Cost: export must check whether incoming knowledge belongs to an existing stamped subject before minting a new one — `SKILL.md`'s `Subject:` guidance makes listing the store an explicit step, because an export that skipped the look re-stamped both folders. UTC rather than local time because archives are consumed on other machines (LADR-008), and a zone-less local stamp from two contributors would not order. **Rejected alternative:** slugs unique only within a subject (an append-log of versioned snapshots) — rejected because it breaks `[[slug]]` resolution (a link would need to name a subject to be unambiguous), the slug-collision merge rules in `SKILL.md`, and `--review`'s inheritance signal (usage would split across duplicate slugs instead of accumulating on the one unit that matters). _(LADR-010 adopted versioning after all, and answers all three objections by keeping the **slug** as the address: a `[[slug]]` resolves if any version exists, `--review` groups usage by slug across versions, and the merge rules were replaced rather than broken. What stays rejected is making slugs unique only **within** a subject — that is the shape that would have forced a link to name one.)_

### LADR-008 — Publish produces an archive under `.context/`; the store is never shared through the repository

- **Date:** 2026-09-19 · **Status:** Accepted (specification — `--publish` and `--consume` have no script yet)
- **Context:** LADR-001 made the tracked `.agents/understandings/` folder the publish destination, reachable through `ai-asset-sync`. The user then ruled that the store is not for GitHub sharing at all: session memory is handed from one person or team to another, not merged into a repository where it would be reviewed, versioned and synced like a skill. A tracked destination also meant every publish changed the repository and needed a PR.
- **Decision:** `--publish [--portable-only]` writes `understandings-<YYYYMMDD-HHMMSS>.zip` to `.context/understandings-publish/` — outside the store, so the index generator never reads it as a subject folder, and gitignored with the rest of `.context/`. The archive mirrors the store exactly: `<subject>-<yyyyMMdd-HHmm>/<slug>.md` with stamps carried verbatim (never re-stamped — that would overwrite when the knowledge was *learned* with when it was *sent*, which the archive name already records), each unit's `<slug>.assets/`, and a regenerated `INDEX.md` covering only the published units. Each archived copy gets `provenance.published_from`; the working copy is untouched. `--consume <zip>` unpacks into the working store and refuses any entry whose resolved path escapes it. Sharing is "send someone the zip": no tracked folder, no fileshare, no service, and `ai-asset-sync` no longer transports Understandings.
- **Consequences:** Nothing published reaches git, so the durability boundary is the archive a human keeps rather than the repository, and a publish needs no PR or code owner. Cross-repo transfer still goes through `--portable-only` (LADR-006). Filtering a subset can leave a `[[link]]` pointing outside the archive: the archived copy drops the brackets and keeps the entry, matching the `provenance.inherited` convention. An incoming unit whose slug already exists locally lands in its own incoming stamped folder as another version of that slug, and the newer stamp decides which the index shows. _(Originally this said the incoming unit must be merged into the local folder, because the same slug in two folders failed the index — LADR-010 removed that failure, and the rule did not outlive its reason.)_ **Rejected alternative:** keep the tracked destination and offer the zip as an extra format — rejected because it leaves the path the user ruled out as the default, and the default is what an agent takes.

### LADR-009 — A specified destination is the approval; only merge and promote still ask

- **Date:** 2026-09-19 · **Status:** Accepted
- **Context:** Publish and consume each described their own ad-hoc override language, and the Guardrails asked for approval before every write to a destination outside the working store — regardless of whether the user had already named one. Asking after a user typed a destination confirms what they just stated, rather than deciding anything.
- **Decision:** One `--path` switch is the target override for every write mode (`--export`, `--publish`, `--consume`); `--consume`'s source stays positional, `--path` is never a source. Writing to a mode's default location, or to an explicit `--path`, needs no approval — the invocation is the consent, and every write is reported (count, destination, slugs) so removing the prompt does not remove the user's chance to notice. Approval stays only where a write changes something the user already has: merging into an existing unit, and promoting to a `*AGENTS.md` or a rule. The `--export` pre-write cut becomes an `AskUserQuestion` recommending "write every candidate" first, rather than a prose list a user could mistake for output.
- **Consequences:** Fewer interruptions on the common path — naming a destination is not followed by a prompt to confirm it. Cost: a mistyped `--path` is no longer caught by a confirmation step; the mitigation is that every write reports where it went, so a wrong destination is visible immediately rather than silently accepted. **Rejected alternative:** keep asking on every write outside the working store regardless of whether a destination was given — rejected because it treats an explicit instruction as still undecided, and a new-file write (unlike a merge) cannot destroy existing knowledge, so the safety case for asking does not hold.

### LADR-010 — An export run is a stamped folder; a slug is a version key, not a unique name

- **Date:** 2026-09-19 · **Status:** Accepted — supersedes LADR-007's store-wide slug uniqueness and LADR-004's folder-reuse clause
- **Context:** LADR-007 made a session extending existing work **reuse** the existing stamped folder, which kept slugs unique store-wide and let the index be a flat list. Three sessions in a row instead minted a new folder *and* a new slug: the same two questions were answered three times each under six slugs, all six indexed as current, so an agent asking either question got three answers with two of them stale. The reuse instruction was present, and was followed as far as listing the store — the step that failed was judging "is this the same question?", which a session that has just done new work reads as new. Two repairs were available: reuse the folder and merge the improvement into the existing file in place, or keep the slug and let the store hold versions. Merging in place was specified first and then rejected by the user: it edits history, and a reader of the merged unit cannot tell a third revision from a first.
- **Decision:** A slug identifies **the knowledge**; a stamped folder identifies **the export run that wrote it**. An export that produces something new or improved creates `<subject>-<yyyyMMdd-HHmm>/` holding *only that run's output* — never a snapshot of the store, and never a copy of an unchanged unit. An improved Understanding is re-written **in full** into the new folder, standing alone, carrying `provenance.supersedes: <previous-folder-name>`. Previous copies are never edited and never deleted. `INDEX.md` lists the **newest version of each slug only**; superseded copies stay on disk, unlisted and exempt from validation. Between two Understandings that conflict, the **newer wins**, decided by folder stamp and falling back to `updated`. An export that produces nothing writes nothing and creates no folder.
- **Consequences:** The store becomes an append-only version log that is still flat to read — one row per slug. Improvements are auditable, since every revision survives and `provenance.supersedes` shows the depth, which is itself signal about how settled the knowledge is. `duplicate_slugs` is retired: the same slug in two folders is now the mechanism rather than an error. **That gives up a real protection** — a typo'd or copy-pasted slug colliding with unrelated knowledge is now indistinguishable from an intentional version, and nothing mechanical catches it. The replacement is procedural: the reconcile step makes reading `INDEX.md` the *first* action of an export, with the four outcomes stated there, because the same rule stated as a prohibition had already been skipped once. _(LADR-011 added a fifth, `has another home`, so that an exclusion on qualifying grounds has a reporting slot instead of becoming prose.)_ Validation exempting superseded copies is what keeps history immutable — validating them would force edits to the past, and a link target pruned later would make an old file permanently invalid. **Rejected alternative:** merge the improvement into the existing unit in place (the first specification) — rejected because it rewrites history, loses the revision depth, and leaves the reader unable to distinguish a settled unit from a freshly-written one. **Rejected alternative:** version within a subject folder so slugs stay unique per-subject — this was already rejected in LADR-007 and stays rejected; it breaks `[[slug]]` resolution, which must name knowledge rather than a revision.

### LADR-011 — `--all` widens the qualifying bar, not only the ask

- **Date:** 2026-09-20 · **Status:** Accepted
- **Context:** `--all` was documented in three places as prompt suppression only — "skip the cut", "write every qualifying candidate without pausing for the user to cut the list". All three describe *who* cuts the list; none describes how tight the agent's own filter should be, and the word "qualifying" defers that entirely to a test the switch never mentions. An `--export --all` over a session carrying six durable lessons wrote **one**, and reported it as a complete export. The behaviour was defensible against the text — the agent never asked, so it honoured `--all` literally, and it excluded five candidates on the "no other home" test because a document elsewhere mentioned each topic. Two further gaps made the loss invisible: the qualifying test did not separate a recorded decision from the reusable reasoning behind it, and "another artefact owns this" was a real exclusion with no slot among the four reconcile outcomes, so it was reported as prose — the precise failure the "report every candidate" line exists to prevent. Same failure class as LADR-006 on the publish side, where a default filter turned an 8-unit store into a 1-unit archive; here the filter was the agent's own judgement rather than a flag.
- **Decision:** `--all` means breadth as well as silence. It waives the user's cut **and** loosens the agent's own qualifying bar, so a marginal candidate is written rather than dropped. The qualifying table gains a row routing "a decision already recorded elsewhere, where the reusable reasoning or diagnostic behind it is not" to the store, because a document recording *what was decided* has no claim on *how to recognise it, re-derive it, or choose again* — an ADR/NFR/LADR carries the verdict, the Understanding carries the failure signature, the miss profile, the diagnostic. The reconcile step gains a fifth outcome, `has another home`, which every genuine exclusion is reported under and which **must name the file**. Precedence is encoded **in the table itself** rather than in prose beside it: the absent-index row is conditional on the qualifying test routing the candidate to the store, and `has another home` is its explicit complement, so the two rows split that case and no candidate maps to both. An earlier draft stated the precedence only in a following paragraph, which left the absent-index row reading unconditionally — the same defect class as the gaps this LADR closes, caught in review.
- **Consequences:** The same invocation now writes every qualifying unit, and an exclusion is auditable against a path rather than a sentence. **This loosens the store's tightest guard, knowingly:** the store will grow faster and will accumulate units whose knowledge is partly covered elsewhere. That is the accepted trade — a thin store fails **silently**, because an under-filled store is shaped exactly like a store with nothing to say, which is also the shape of the defects it documents; an over-full store is visible and prunable through `--review`. The sharper test also costs the "it mentions the topic" shortcut: deciding `has another home` now means asking what question the other document answers, which is a judgement rather than a lookup. **Rejected alternative:** keep the strict bar and rely on agent judgement under `--all` — rejected because that arm was already run and produced a one-unit complete dump from a six-unit session; the text permitted the outcome, so emphasis or exhortation would not have changed it. **Rejected alternative:** have `--all` bypass the qualifying test entirely and write every candidate — rejected because that test is what keeps toolchain knowledge and already-homed documentation out of the store (Key Behaviors, "the store is for the product, not the process"); removing it under a switch would make `--all` the fastest way to fill the store with things that have homes.

## Key Behaviors

- **"Understanding" is a term of art, borrowed from Adrian Tchaikovsky's _Children of Time_.** In the novel an Understanding is knowledge distilled and passed to a generation that never had the experience which produced it — which is exactly the contract here: the originating session is discarded, the transferable knowledge survives. Do not "clarify" the name to `learnings`, `notes`, `lessons`, or `memories`. Those all invite session logs; this one does not, and the distinction between a log and an Understanding is the whole design.
- **A unit is a question and its answer, not a topic and some notes.** Frontmatter carries the `question` a reader has at the moment the knowledge applies; the body's `## Answer` addresses that and nothing wider. The pairing is a constraint, not a format: one question has one answer, so an answer that outgrows its question means the question was too narrow, and a question no answer covers means it was too broad. This replaced a situation-shaped `trigger` field, which could sprawl — the eval rounds found exactly that defect, a trigger matching cases its own body could not answer.
- **The export's reconcile step is a step, not a prohibition — and that distinction is the whole fix.** The rule "reuse the folder, do not re-stamp" existed as a Non-Negotiable here, a sentence in `SKILL.md` and a sentence in the README, and was still violated by the next export, which re-stamped both folders and rewrote every unit. The repair was not stronger wording: it was making *read `INDEX.md`* the numbered first action of the procedure, with the outcomes stated there. A rule outside the write procedure is consulted only if the agent happens to recall it at the moment it applies, and a rewrite is exactly when an agent is least likely to pause. An edit that demotes the reconcile step back into guidance reinstates the defect.
- **"Same question" is the one judgement in the write path with no mechanical check behind it,** so it absorbs all the ambiguity — and an agent that has just done new work is primed to read its own question as new. Measured before LADR-010: nine units, two questions, six slugs, zero reuse, five runs. Each session judged its question new in good faith because each was narrower than the last. This is why the test is stated generously ("would an existing unit's question be *answered* by what you are about to write?") and why `improved` is the tie-break. Tightening it re-creates the pile.
- **Retiring `duplicate_slugs` gave up a real protection, knowingly.** It caught a typo'd or copy-pasted slug colliding with unrelated knowledge — a class of error nothing now detects, because a repeated slug is indistinguishable from a deliberate revision. The replacement is procedural, not mechanical. Do not "restore" the check: it would make every version chain a validation failure and silently disable versioning.
- **Validation and the index see current versions only; history is exempt and immutable.** Validating superseded copies would force edits to the past, and a `[[slug]]` pruned later would leave an old file permanently invalid. Folder-level problems (unstamped, empty, legacy shape, stray root file) are still reported unconditionally, since they belong to no single version. A `[[slug]]` resolves against **every** version, and `--review`'s inheritance signal counts **any** version — both because a slug names the knowledge rather than a revision.
- **`provenance.inherited` is read back, and that is the point of it.** `--review` computes which units nothing has ever inherited and flags them: the question probably does not match what anyone asks. LADR-005 justified the field as a usage signal, and for several rounds it was decorative — validated on write, never read. An edit that stops writing it, or stops `--review` reading it, removes the only evidence the store has about its own worth. The signal self-suppresses in a store where no unit records inheritance yet, so a young store is not flooded with false positives.
- **Decay is advisory, never a validation failure.** A contested, unused or overdue unit is not *wrong*, so `--review` prints and exits `0`. Folding decay into the problem list would train agents to ignore the problem list, which is where real defects are reported.
- **Outcomes are a first-class kind of unit, and the only kind with no `*AGENTS.md` fallback.** What a piece of work produced — requirements distilled from meetings, the issues and PRs it opened and their state, what was specified but left unbuilt — is knowledge a next session needs first and that no context document carries, because an `*AGENTS.md` records what the code does rather than what is still owed. The ban on session logs is about **shape**: a narrative of the work is out, the durable artifacts and their state are in. These units go stale fastest, so each carries its date and the command that re-checks it.
- **The store is for the product, not the process.** An Understanding carries functional and non-functional knowledge about the system being built; knowledge about the agent toolchain that produced it — a skill's internals, a scanner's dependencies, a workflow's trigger filters — belongs in the nearest `*AGENTS.md`. This was learned the expensive way: the store accumulated eight units across ten eval rounds, and on review six were plumbing about the repo's own skills. Effort spent learning something does not qualify it; a toolchain quirk can cost an afternoon and still not be memory about the product.
- **Understandings are evidence; rules are orders.** The governance half of this design lives in `.github/instructions/meta/understandings.instructions.md`, not here, because importing must work at session start without anyone invoking the skill. Editing one side without the other splits the contract.
- **A session splits into several slugs inside one subject.** One Understanding per question, each standing alone, grouped under the subject it came out of. Merging a session's lessons into one unit to keep the count down produces a unit whose question matches everything and therefore nothing — the subject folder is what keeps them together, not a shared file.
- **Consumed units land as `confidence: observed`,** whatever they claimed at the source. They were verified against a setup that may differ.
- **A `verified` unit is not a correct unit.** Two independent agents asked to check one against the code found a false claim in it — the unit asserted a behavior that reading the source disproves. `confidence` records how the knowledge was obtained, not that it is right, which is why the import protocol tells agents to verify rather than defer. An edit that softens that instruction removes the only mechanism that catches this.
- **Promoted knowledge does not stay in the store.** Once an Understanding is folded into a `*AGENTS.md` or a rule, the store copy is a competing copy that will drift. The naming-vocabulary lesson recorded above in Key Behaviors was exported as a unit first and then removed for exactly this reason.
- **Promotion is the exit, not a cleanup chore.** An Understanding proven across many tasks belongs in a `*AGENTS.md` or a rule, which load without a skill invocation. Leaving it in the disposable store means re-earning it every workspace.
- **Export/import are session↔disk; publish/consume are workspace↔workspace.** The first naming made `--export` mean "copy to a tracked path", which reads as publishing to anyone who thinks of export as getting a session's memory out of the conversation — the switch did not do what its name promised, and the mode was invoked expecting analysis. Do not collapse the two pairs back together.
- **The frontmatter parser is hand-rolled** because PyYAML is not available in this environment. It handles flat scalars, top-level lists, a nested map, and a list inside that map (`provenance.inherited`) — and nothing deeper. Adding a frontmatter field with more structure means extending `parse_frontmatter`, not just the template; the `inherited` list was exactly that case and the naive version silently clobbered the whole `provenance` map into a list.
- **The generator's `[store-dir]` argument stays positional, not `--path`.** It is a script CLI that predates the skill's switch surface (`understanding_index.py [store-dir] [--review]`), and the skill's `--path` (LADR-009) is documented separately as procedure, not script flags. Changing the script's contract to match would break every command already written against it for a cosmetic alignment only — a known, accepted inconsistency, not an oversight.
- **Reference validation is generic; parsing is the narrower constraint.** Any frontmatter list — top-level, or one level inside a map — has its `[[slug]]` entries resolved by `dangling_references`, so a field added to the template is checked without touching the generator. Only bracketed entries are references; a bare string is a historical note, which is how `provenance.inherited` survives naming an Understanding that was later pruned or promoted. What still needs a code change is a field with a *shape* the parser does not handle — and the shape that bites is not only the deep one. A list written in YAML flow style (`links: [[a]]`) parses as a plain **scalar**, never reaches the walk, and used to let a dangling reference exit `0`; it is now reported as its own problem naming the block form, rather than the parser guessing whether `[[a]]` is one reference or a nested sequence. Validation used to be per-field (`dangling_links` and `dangling_inherited`, each by name), which let a dangling reference in an unrecognised field exit `0`; the two walkers were merged once the second one proved the case. The parser reads **block lists only**; a flow-style list (`links: [[a]]`) becomes a scalar and is invisible to the reference walk, so `inline_sequences` names that shape as a problem rather than silently passing it. Two traps when touching it: the check must cover a flow sequence **nested in a map** (`provenance.inherited`) as well as a top-level one — fixing only the top level repeats the per-field mistake one level up — and it must require the closing `]`, or a description reading `[draft] …` is reported as a list.

## Test References

No automated tests. The generator's validation paths (missing/placeholder `description`/`question`/`scope`/`confidence`/`updated`/`provenance.*`, slug-vs-folder mismatch, invalid `scope`/`confidence`, a non-existent `agents_context` path, a slug not matching its file name, dangling `[[slug]]` references in a top-level list, in `provenance.inherited`, and in a field the generator has never heard of, a unit left in the old per-unit-folder shape, a unit stranded at the store root, an empty subject folder, empty store, absent store) its lineage validation (resolving, dangling, and deliberately unbracketed `provenance.inherited` entries), a list written in YAML flow style rather than block style, its flow-sequence detection (top-level, nested in a map, block form, and prose beginning with `[`), the `--review` report (inherited vs orphaned, contested, and both staleness thresholds), and its argument handling (`--help`, `--review`, unknown flag, surplus argument) were exercised manually against fixtures. `parse_frontmatter` additionally has direct assertions for the nested-list case, same-indent list items, a scalar following a list, and absent frontmatter. A fixture carrying dangling references in both `links` and an unrecognised sibling list (`supersedes`) confirms the generic walk described in Key Behaviors: **both** are reported, and removing the `links` dangler still exits `1` on the unrecognised one. That fixture was written when validation was per-field and the second dangler escaped with exit `0`; it is kept because it is the regression test for that gap. Re-run them after touching `parse_frontmatter` — the list-under-key branch in particular is easy to break in a way that silently drops `links` instead of erroring. The subject-stamp check (LADR-007) was exercised against fixtures for: a correctly stamped folder, `_unfiled` unstamped, a folder missing the stamp, and stamps with a plausible-but-wrong shape (a 7-digit date, a 3-digit time) — all reported rather than silently accepted, each with a remedy naming its own fix (unstamped, malformed widths, and a stamp with no subject in front are three different messages). **The same slug across two stamped folders was a fixture for the duplicate check and is now a fixture for versioning**: it exits `0` and indexes the newer copy only. LADR-010's grouping has its own battery — two and three versions of one slug (newest wins, one row); a superseded copy carrying a dangling `[[link]]` and a non-existent `agents_context` (no problem reported) against a control putting the same defects on the current copy (exit `1`); a `[[link]]` resolving to a slug whose newest copy sits in an older folder; `--review` where only a *superseded* copy records the lineage (the target is still not flagged never-inherited) against a control orphan that is. The whole pre-LADR-010 battery was re-run afterwards — stray root file, stamp-only folder, legacy folder shape, malformed stamp, slug/filename mismatch, flow sequences top-level and nested, a quoted dangling reference, and prose beginning with `[` — with identical results. Two defects found in a later branch review have their own fixtures: a **block scalar** (`description: >-`, `|`, and an indent-indicator form such as `|2-`, at both nesting levels) which used to index as its own header with exit `0`, against controls of prose containing `>` and `|` and a value beginning `->` that must not be flagged; and a **scalar `provenance.inherited` on a superseded copy**, which used to be iterated character by character — losing the real target and spuriously setting `lineage_recorded`, so every unit reported as never inherited with nothing printed and exit `0`. A `"[[slug]]"` reference written in quotes has its own fixture: quoted, it once bypassed both the dangling check (exit 0) and the lineage reader (`--review` still reported the target as never inherited); the parser now unquotes scalars and list items, and the fixture confirms a quoted dangling link exits 1 and a quoted `provenance.inherited` entry counts as usage.
